Install mode

Docker/Podman need no ROS install on this machine at all -- linorobot2's own docker/Dockerfile builds everything (including sensor drivers) inside the image. Useful on unsupported OS versions, or when you'd rather not touch the host at all. Native builds directly on this machine instead.

1. Build image

Writes docker/.env and a docker/docker-compose.override.yaml mapping the base serial port and laser device into the bringup service (the documented manual step in linorobot2's own docs/docker.md), then clones linorobot2 (if not already present) and runs the image build. Sensor drivers install inside the image via linorobot2's own install.bash -- that's the documented Docker build path itself, not something Console runs on this host.

2. Host udev rules

The image already contains the sensor drivers -- this only creates the persistent /dev/<sensor> symlink on the host, using Console's own native udev-rule commands (same as the native Laser/Depth sensor install cards above), not install.bash.

3. Run a service

Runs in the foreground through the same console pane as everything else in Console -- Stop sends the container(s) a normal compose stop signal. Start kasmvnc alongside bringup/slam/etc. (in a second Console tab, since each occupies the one exec slot) for GUI output from any of them.

Robot bringup

bringup.launch.py starts its own micro-ROS agent internally (base_serial_port/transport/port below) -- Console does not launch a separate agent alongside it, since two agents on the same port would just fight each other. The manual agent controls in Settings are for other uses only (e.g. testing agent connectivity on its own).

These select the sensor model via LINOROBOT2_LASER_SENSOR/LINOROBOT2_DEPTH_SENSOR, using whatever connection details are hardcoded in linorobot2_bringup's own launch files (e.g. YDLIDAR/RPLIDAR already use persistent /dev/ydlidar //dev/rplidar udev symlinks). For a custom serial path, baudrate, or the LiDAR-over-WiFi-UDP bridge, use the Laser driver card on the Sensors tab instead of going through Bringup.

Visualize (RViz via browser)

Most robot computers are headless -- RViz has nowhere to open a window on. This runs RViz against a virtual display and serves it over noVNC, the same idea as the kasmvnc service in linorobot2's own docker/docker-compose.yaml, but native (no Docker) to match how the rest of Console installs things. Works whether you're viewing from the robot computer itself or a separate laptop on the network.

Heavier than the rest of Console -- RViz is a full Qt/OpenGL app, and on a small SBC (limited CPU, 4GB RAM class) running it headlessly through Xvfb adds real CPU/memory load on top of Bringup/Nav2. On constrained hardware, prefer the plain Sensors tab's /scan canvas viewer (much cheaper) and only reach for this when you actually need the full map/costmap/TF view.

    Magnetometer calibration

    Spins the robot in place for roughly a minute. Clear the area first. Resulting bias values are shown below for manual entry into config-engine's MAG_BIAS field -- the two tools stay independent, no auto-sync.

    Laser driver

    Runs the laser driver on its own, independent of Bringup and of the micro-ROS agent -- the LiDAR talks to the robot computer directly (USB serial or its own WiFi-UDP relay), not through the MCU/agent link.

    The MCU relays raw LiDAR UART bytes as UDP datagrams to this port (its LIDAR_PORT/AGENT_IP setting in config-engine must point at this robot computer). Console bridges them into a local persistent serial device with socat, then points the driver at that device -- there's no other consumer for this feed today.

    Configure, build, and flash firmware (robot_config_engine)

    linorobot2 and linorobot2_hardware stay separate repos with separate concerns -- Console doesn't reimplement any board/PlatformIO/flashing knowledge. linorobot2_hardware's own robot_config_engine ("config-engine") already does board detection, header generation, PlatformIO build, and flashing, so this just launches config-engine itself inside a Docker container (so PlatformIO/board toolchains don't need to be installed anywhere either) and hands you a link to its real web UI. Everything past that point happens in config-engine's own interface.

    The board has to be physically attached to wherever the container actually runs -- leave "Run on" blank to launch it here, or set it to launch (over SSH) on the machine the board is plugged into instead, e.g. if you're driving Console from a laptop but the board is on a separate headless robot computer. Uses docker specifically (not Podman) -- keep to one container engine per workflow, since they don't share image storage.
